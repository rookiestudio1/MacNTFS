# MacNTFS

English | [繁體中文](README.md)

An Xcode project that gives macOS 15.4+ read-write NTFS support using Apple **FSKit** and **libntfs-3g**.

- Automatically mounts NTFS drives at `/Volumes/<label>` when they are connected (via DiskArbitration and FSKit probe order)
- Mounts multiple drives at the same time
- A menu bar app for mounting, unmounting, remounting read-only, and switching back to read-write

## Project layout

```
project.yml                 XcodeGen spec (change signing and bundle IDs here)
MacNTFS.xcodeproj           Generated by `xcodegen generate`
MacNTFS/                    SwiftUI menu bar app (DiskArbitration monitoring, diskutil mount/unmount)
NTFSFSExtension/            FSKit file system extension (Objective-C + C, Swift entry point)
  Bridge/ntfs_bridge.[ch]   C bridge to libntfs-3g (keyed by MFT record number)
  NTFSBlockDevice.m         FSBlockDeviceResource → libntfs-3g device callbacks (with sector alignment)
  NTFSFileSystem.m          probe / load / unload / fsck
  NTFSVolume.m              FSVolume operations (read/write, directories, xattrs, rename…)
Tools/ntfs-bridge-test/     CLI that tests the bridge against a disk image
Scripts/build-ntfs3g.sh     Downloads and builds libntfs-3g (arm64 + x86_64 universal static library)
ThirdParty/ntfs-3g/         Prebuilt libntfs-3g.a and headers (LGPL 2.1)
Scripts/make-appicon.sh     Generates the app icon asset catalog from ntfs.png
ntfs.png                    Source image for the app icon (the menu bar icon is an SF Symbol, not this image)
build/                      Build products (in .gitignore)
docs/superpowers/specs/     Design documents
```

Build products always go under `build/`, set by `SYMROOT` in `project.yml`, regardless of the global build location in Xcode's preferences. This keeps a single product path per project. If copies of the app exist at several paths, the file system extension list in System Settings shows duplicate entries.

## Building

Requirements: macOS 15.4+ (developed on macOS 26.5 / Xcode 26.6), Xcode 16.3+, and `xcodegen` from Homebrew (only needed after editing `project.yml`).

```bash
# 1. (Optional) Regenerate the Xcode project
brew install xcodegen
xcodegen generate

# 2. Build libntfs-3g (Xcode's pre-build script also runs this on the first build)
Scripts/build-ntfs3g.sh

# 3. Open MacNTFS.xcodeproj in Xcode, or:
xcodebuild -scheme MacNTFS -configuration Debug build
# The product is at build/Debug/MacNTFS.app
```

To change the app icon, replace `ntfs.png` in the project root with the new image (1024x1024 recommended), run `Scripts/make-appicon.sh` to regenerate the asset catalog, and rebuild.

### Code signing (required)

FSKit extensions need the `com.apple.developer.fskit.fsmodule` entitlement, and macOS only loads extensions **authorized by a provisioning profile**. Ad-hoc signed extensions are not loaded. Set your Team ID as `DEVELOPMENT_TEAM` in `project.yml` (or pick a Team under Signing & Capabilities in Xcode), make sure the App ID has the FSKit capability enabled, and then run `xcodegen generate`.

The default bundle IDs are `com.rookiestudio.MacNTFS` and `com.rookiestudio.MacNTFS.NTFSFSExtension`. You can change both in `project.yml`; also update the constants in the app's `ExtensionStatus.swift` to match.

## Installing and enabling

1. Move `MacNTFS.app` to `/Applications` and launch it once.
2. Go to **System Settings > General > Login Items & Extensions > File System Extensions** and enable **MacNTFS**.
3. Connect an NTFS drive. DiskArbitration follows `FSProbeOrder` (500/1500/3500 for this extension, lower than the built-in `ntfs.fs` at 1000/2000/4000), so MacNTFS probes the drive first and mounts it under `/Volumes`.
4. If the built-in read-only driver still mounts the drive first (`DAVolumeKind == ntfs`), the menu bar app shows 「系統唯讀掛載」 (system read-only mount) and offers 「改用 MacNTFS 掛載」 (mount with MacNTFS). The app's interface is currently in Traditional Chinese only. This fallback runs `diskutil unmount` first, then `mount -F -t ntfs3g` with administrator privileges.

The equivalent commands for doing this by hand:

```bash
diskutil mount disk4s1                 # Read-write mount (via diskarbitrationd → FSKit)
diskutil mount readOnly disk4s1        # Read-only mount
diskutil unmount disk4s1               # Unmount
sudo mount -F -t ntfs3g -o rdonly /dev/disk4s1 /Volumes/NTFS   # Fallback: call FSKit directly
```

## Testing

### Bridge layer (no signing or FSKit needed)

Create a disk image with `Scripts/make-test-image.sh`, then run `ntfs-bridge-test`:

```bash
# Create a test image (the first run builds a host mkntfs into ThirdParty/build/host-tools/)
Scripts/make-test-image.sh 512 /tmp/test.img

xcodebuild -scheme ntfs-bridge-test -configuration Debug build
build/Debug/ntfs-bridge-test /tmp/test.img
```

The tests cover: probe, read-write mount, statfs, mkdir, create/read/write/unaligned write/truncate, case-insensitive lookup, xattrs (named streams), symbolic links, hard links, characters forbidden on Windows, timestamps and flags, directory enumeration (full and paged by cookie), rename and replace, delete, volume label, and read-only remount with EROFS.

### Performance measurement

The `bench` subcommand measures the bridge + libntfs-3g directly against an image without going through FSKit, so changes to the bridge can be checked right away:

```bash
Scripts/make-test-image.sh 512 /tmp/bench.img   # Use a fresh image for every run
build/Debug/ntfs-bridge-test bench /tmp/bench.img
```

It measures six phases: sequential write, sequential read, sequential overwrite, random read, small file creation, and directory traversal.

To attribute device traffic to a phase, set `BENCH_TRACE` to record every device I/O during the "small file creation" phase as `r|w <offset> <length>`:

```bash
BENCH_TRACE=/tmp/small.trace build/Debug/ntfs-bridge-test bench /tmp/bench.img
```

Group the entries by size and offset to see which NTFS structures the traffic goes to.

**Look at device reads, device writes, and the amplification factor, not just elapsed time.** The image usually sits entirely in the page cache, so elapsed time mostly reflects CPU and call overhead. Device I/O counts are deterministic, so before/after comparisons have no noise. The amplification factor is the bytes the device actually moved divided by the logical bytes requested. Every extra MFT read/write or runlist rebuild in the bridge shows up directly in this number.

### End-to-end

```bash
# Use a disk image as a stand-in for a drive
hdiutil attach -nomount test.img          # Prints /dev/diskN
diskutil mount diskN                      # Should be mounted by MacNTFS at /Volumes/TestNTFS
mount | grep ntfs3g
diskutil unmount diskN && hdiutil detach diskN

# Debug logs
log stream --predicate 'subsystem == "com.apple.FSKit" OR subsystem == "com.rookiestudio.MacNTFS"'
pluginkit -m -p com.apple.fskit.fsmodule  # Check that the extension is registered
```

## Troubleshooting

### `Module com.rookiestudio.MacNTFS.NTFSFSExtension is disabled!`

The extension is installed and signed correctly but hasn't been enabled in System Settings yet. Go to **System Settings > General > Login Items & Extensions**, click the ⓘ button next to **File System Modules**, and turn on **MacNTFS File System Extension**.

The enabled state is stored in `~/Library/Group Containers/group.com.apple.fskit.settings/enabledModules.plist`. Only the toggle in System Settings can write it; `pluginkit -e use` has no effect on it.

### Checking whether the system sees the extension

```bash
pluginkit -m -p com.apple.fskit.fsmodule -vvv   # Should list com.rookiestudio.MacNTFS.NTFSFSExtension
plutil -p ~/Library/Group\ Containers/group.com.apple.fskit.settings/enabledModules.plist   # Appears only after enabling
plutil -p ~/Library/Group\ Containers/group.com.apple.fskit.settings/probeOrder.plist       # Probe order
```

If `pluginkit` doesn't list it, the app usually hasn't been registered with LaunchServices yet:

```bash
/System/Library/Frameworks/CoreServices.framework/Frameworks/LaunchServices.framework/Support/lsregister -f /Applications/MacNTFS.app
```

### It used to work, but now drives won't mount

First check whether the appex lost its signature. **Don't build with `CODE_SIGNING_ALLOWED=NO`.** That produces an ad-hoc signed build without a provisioning profile and overwrites the working copy in the build products folder. After that, `diskutil mount` only reports:

```
Volume on diskN failed to mount
```

Rebuilding with normal signing fixes it. The enabled state in System Settings is not lost.

### Checking the signature

```bash
codesign -d --entitlements - --xml /Applications/MacNTFS.app/Contents/Extensions/NTFSFSExtension.appex | plutil -p -
```

You must see `com.apple.developer.fskit.fsmodule => true`, and the appex must contain `Contents/embedded.provisionprofile`. Without a provisioning profile, AMFI won't load the extension.

## Design notes

- **No long-lived libntfs-3g inodes**: each operation does `ntfs_inode_open` → operate → `ntfs_inode_close`, so the same inode is never open twice and MFT records stay consistent (the same approach as the ntfs-3g FUSE driver).
- **Case-insensitive, case-preserving**: libntfs-3g's case-sensitive flag is cleared, and an identity lowercase table keeps names from being lowercased during enumeration.
- **Sector alignment**: `FSBlockDeviceResource` requires sector-aligned I/O, so the bridge does read-modify-write for unaligned requests.
- **xattrs → named `$DATA` streams**: macOS `com.apple.*` extended attributes are stored as NTFS named streams.
- **Permissions**: no NTFS user mapping. uid/gid default to 99 (equivalent to Finder's "Ignore ownership on this volume"). `FILE_ATTR_READONLY` maps to removing the write bits, and `FILE_ATTR_HIDDEN` maps to `UF_HIDDEN`.
- **Hibernated Windows volumes**: probe still reports them as usable, and libntfs-3g falls back to read-only when mounting.

## Known limitations

- Kernel-offloaded I/O is not supported, so throughput for large files is limited by XPC round trips.
- Formatting and repair are not supported (`fsck` only checks whether the volume can be parsed and whether it is hibernated).
- Writing NTFS compressed or encrypted files is not supported.
- Rename is done as link + unlink and is not atomic.
